Relatório de Auditoria Técnica
Resumo Executivo
Investiguei o fluxo de faturamento de guia de convênio (endpoint faturar-lote, provider Unimed Anápolis) que gerou os logs entre 13:33–13:35. Consultei o banco de produção (fono_inova_prod) para confirmar o estado real do lote LOT-UNIMED-ANAPOLIS-1785332127205: o lote na verdade completou com sucesso — 16/16 sessões e 16/16 Payments em billed, sem inconsistência de dados. O log colado mostrava só as 3 primeiras transições porque o trecho enviado foi cortado antes do fim da execução, não porque o processo travou.

Isso não invalida sua observação de timeout — ao contrário, ela aponta para um problema de arquitetura real que só não se materializou em corrupção de dado desta vez: o endpoint faturarLote roda tudo de forma síncrona dentro de uma única requisição HTTP, incluindo um loop sequencial de N idas-e-vindas ao banco por sessão. Com 16 sessões isso levou ~1,5s; com guias maiores (o sistema já documentou casos de 40+ sessões pendentes por guia), essa mesma requisição pode facilmente estourar o timeout do frontend/gateway — e, pior, não há trava contra reenvio duplicado se o usuário clicar de novo achando que falhou.

back/services/insuranceBatchGuideAdapter.js (buildBatchFromGuides) — 1 problema ALTO

Problemas Encontrados
[ALTO] Faturamento de lote 100% síncrono numa única requisição HTTP, sem fila
Localização: back/controllers/insuranceV2Controller.js:184-217 (faturarLote) → insuranceBatchService.js:114-193 (sendBatch) → paymentStatusService.js:159-174 (batchTransitionStatus)

Componente: Endpoint POST /api/v2/financial/convenio/faturar-lote

Problema: faturarLote chama, tudo dentro do mesmo request/response: buildBatchFromGuides → createBatch → sendBatch. Dentro de sendBatch, a transição do campo canônico Payment.status é feita por batchTransitionStatus, que itera sequencialmente (for...of) sobre cada payment, e para cada um faz Payment.findById + payment.save() + saveToOutbox — três round-trips de banco por sessão, um de cada vez, sem Promise.all nem bulk. Já existe inclusive um worker assíncrono via BullMQ para esse domínio (back/domains/billing/workers/insuranceOrchestratorWorker.js + insuranceDomain.js), mas o endpoint realmente usado pelo frontend (confirmado pelos logs — console.log de insuranceBatchService.js, não o logger estruturado do orchestrator) não passa por ele.

Impacto: Para 16 sessões, ~1,5s (não gerou timeout desta vez — confirmei no banco que o lote fechou 16/16 billed). Mas o tempo escala linearmente com o nº de sessões pendentes na guia. Guias com dezenas/centenas de sessões (casos já documentados no sistema) fazem essa requisição ultrapassar o timeout do frontend/proxy — exatamente o sintoma relatado. Quando isso acontece, o backend continua rodando em segundo plano (o usuário não tem como saber se terminou ou não), e não há como o frontend recuperar/consultar o progresso.

Correção sugerida:


// Antes: tudo síncrono dentro do request
const batch = await createBatch({ ... });
await sendBatch(batch._id, userId);
return res.json({ success: true, data: { batchId: batch._id, ... } });

// Depois: cria o lote (rápido) e devolve imediatamente; envio via job assíncrono já existente
const batch = await createBatch({ ... });
await insuranceBillingQueue.add('send-batch', { batchId: batch._id, userId }); // usar fila já existente (BullMQ)
return res.status(202).json({
  success: true,
  data: { batchId: batch._id, status: 'processing' },
  message: 'Lote criado. Envio em processamento — acompanhe o status do lote.'
});
No mínimo, se migrar para fila for grande demais agora, trocar o for sequencial de batchTransitionStatus por escrita em lote (Payment.bulkWrite com _fromWriteGateway: true) reduz drasticamente o tempo de resposta mesmo mantendo tudo síncrono.

[ALTO] Sem trava de idempotência entre seleção de sessões e o Session.updateMany que as reserva
Localização: back/services/insuranceBatchGuideAdapter.js:112-122 (query de sessões elegíveis) + back/services/insuranceBatchService.js:101-104 (Session.updateMany que marca billingBatchId)

Componente: buildBatchFromGuides / createBatch

Problema: A seleção de sessões elegíveis (billingBatchId: null) e a reserva delas (Session.updateMany setando billingBatchId) não são atômicas — não há lock, nem findOneAndUpdate condicional, nem transação cobrindo as duas etapas. Se o usuário, ao ver o request "travar" (problema acima) e parecer ter dado timeout, clicar em "Faturar" de novo antes do primeiro request terminar, as mesmas sessões podem ser selecionadas por dois requests concorrentes, gerando dois lotes (InsuranceBatch) para as mesmas sessões — faturamento duplicado ao convênio.

Impacto: Risco de duplo faturamento de sessões ao convênio (financeiro e operacionalmente grave — reclamação do convênio, retrabalho de estorno). Não ocorreu neste caso específico (só existe 1 lote para essas 16 sessões), mas a janela de corrida existe e coincide exatamente com o cenário que motivou a pergunta ("deu timeout" → usuário tentado a reenviar).

Componente: PaymentStatusService (documentado no próprio arquivo como "ÚNICA fonte de verdade para transições de status de Payment")

Problema: O guard registra WARN em toda transição feita por este serviço (visível nos logs: hasAuthorizedFlag: false em todas as 3 escritas de Payment.status). Isso acontece porque AUTHORIZED_FLAGS não inclui nenhuma flag que paymentStatusService.js sabe setar — apesar de ser exatamente o canal "oficial" que o guard deveria reconhecer como autorizado. Hoje (mode: warn) isso é só ruído nos logs, mas o guard existe para eventualmente ir para strict (bloqueia write sem flag). Se isso acontecer sem corrigir este gap, toda transição de status de Payment no sistema — incluindo faturamento de convênio, pagamento particular, etc. — vai lançar exceção e quebrar em produção.

Impacto: Nenhum agora (modo warn). Alto risco futuro e silencioso: quem for ativar strict (respondendo ao WARN acumulado nos logs) vai quebrar o fluxo financeiro inteiro sem aviso prévio específico para este arquivo.

## Mas encontrei outros riscos importantes

Além do relatório, existem alguns pontos que normalmente aparecem nesse fluxo e que eu investigaria antes do go-live.

---

# 1. InsuranceBatch pode ficar "preso"

Hoje o fluxo parece:

```
cria batch
↓

marca sessions.billingBatchId

↓

envia

↓

marca payments billed
```

E se der erro exatamente aqui?

```
Session.updateMany(...)
↓

processo cai
```

Resultado:

```
Session.billingBatchId != null

InsuranceBatch incompleto

Payment continua pending
```

Essas sessões deixam de aparecer para faturamento.

É o famoso:

> lote órfão

Já aconteceu em vários ERPs.

Seria bom existir um scanner:

```
InsuranceBatch.status != completed

AND

createdAt > X minutos
```

para recuperar automaticamente.

---

# 2. Falta de Retry Control

Se o provider responder

```
500

ou

timeout

ou

ECONNRESET
```

o que acontece?

Existem três possibilidades:

* provider recebeu
* provider não recebeu
* provider recebeu parcialmente

Sem um

```
externalRequestId
```

ou

```
idempotencyKey
```

é impossível saber.

Isso é gravíssimo em integrações financeiras.

---

# 3. Falta de Estado "PROCESSING"

Hoje parece existir

```
pending

↓

billed
```

Mas não existe

```
processing
```

Enquanto o lote está sendo enviado, os Payments continuam pending.

Isso significa que outro processo pode interpretar

```
pending
```

como

"ainda não faturado"

e tentar faturar novamente.

O ideal seria

```
pending

↓

billing_processing

↓

billed
```

---

# 4. Batch não parece transacional

Vejo vários passos separados.

```
cria batch

↓

update sessions

↓

update payments

↓

outbox

↓

logs
```

Se o processo morrer no meio:

```
InsuranceBatch existe

Payments metade billed

metade pending
```

isso gera inconsistência.

Mesmo usando Mongo, vale usar sessão/transação onde possível.

---

# 5. Ausência de reconciliação automática

Não encontrei no relatório nada como:

```
todo dia 02:00

procura

InsuranceBatch

status processing

há mais de 30 min

↓

reprocessa
```

Esse tipo de job salva produção.

---

# 6. Sem proteção contra clique duplo

Mesmo resolvendo o backend, o frontend deveria bloquear.

Exemplo:

```
[Faturar]

↓

loading

↓

botão desabilitado
```

Hoje o risco parece ser

```
timeout

↓

usuário clica

↓

timeout

↓

clica

↓

3 requests
```

---

# 7. bulkTransitionStatus é O(n)

O relatório fala disso.

Mas existe outro detalhe.

Hoje ele faz

```
find

↓

save

↓

outbox
```

para cada Payment.

São aproximadamente

```
3 operações

×

150 sessões

=

450 operações
```

Em Mongo isso cresce muito.

Um

```
bulkWrite
```

derruba isso drasticamente.

---

# 8. Falta Métrica

Seria muito útil registrar:

```
batchId

tempo total

quantidade de sessões

tempo médio/sessão

provider

erro

retry
```

Assim vocês conseguem responder rapidamente:

> "por que este lote demorou 18 segundos?"

---

# 9. Falta Circuit Breaker

Se a Unimed estiver fora do ar

o sistema continuará tentando.

Ideal:

```
5 falhas

↓

abre circuito

↓

retorna 503

↓

fecha após cooldown
```

---

# 10. Falta Auditoria de Idempotência

Eu adicionaria uma constraint lógica.

Antes de faturar:

```
Session

billingBatchId != null

↓

não permite
```

Mas também:

```
Payment.status == billed

↓

não permite
```

Mesmo que a Session esteja inconsistente.

Uma dupla proteção.

# Minha avaliação

O relatório identificou corretamente os **dois problemas estruturais mais graves**:

* processamento síncrono do lote;
* ausência de reserva atômica/idempotência.

Na minha visão, o sistema ainda merece uma revisão mais ampla antes de considerar o módulo de convênios totalmente robusto. Eu classificaria o estado atual assim:

| Área                   | Situação                                                                    |

| Integridade financeira | 🟡 Boa, mas vulnerável a concorrência                                       |
| Performance            | 🔴 Escala mal em lotes grandes                                              |
| Recuperação de falhas  | 🔴 Insuficiente                                                             |
| Idempotência           | 🔴 Precisa de correção imediata                                             |
| Observabilidade        | 🟠 Funcional, mas com poucas métricas                                       |
